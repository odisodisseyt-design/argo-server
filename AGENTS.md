# ARGO — правила работы

Проект состоит из двух частей:
- **Сервер** — `/root/text-world` (Python, FastAPI). Источник правил, памяти и resolver.
- **Клиент** — `/root/text-world/android` (Kotlin/Compose), отдельный Git-репозиторий `argo`. Только отрисовка решений сервера.

## Разделение ответственности

- Правила хода, бросок, урон, здоровье, вероятности, состояние мира — только на сервере (`server/engine.py`, `server/resolver.py`).
- Клиент не считает и не генерирует игровые значения. Он показывает только то, что прислал сервер: `presentation`, `character`, `ui_manifest`, `outcome_text`.
- Не показывать игроку: `reason_code`, traceback, внутренние ID, сырые имена полей, логи, request id, warnings, event types.
- Игрок получает только whitelist из `server/dto.py`. Новое поле наружу — только через DTO и только после явного решения.

## Изменения и контроль

- Изменения вносит **главный агент**. `reviewer` только читает и возвращает находки: он не может править файлы и запускать команды.
- Не запускать более одного `reviewer` одновременно. Дождаться результата, разобрать находки, затем править.
- Ничего не устанавливать: пакеты, зависимости, инструменты, LSP, форматтеры — только после отдельного разрешения.
- Не менять `~/.config/opencode/opencode.json`, модели, провайдеры и локальные плагины (`hide-paid-models`, `model-availability`) без явной просьбы.
- При неоднозначности задать вопрос и дождаться решения, а не догадываться.

## Оркестрация (обязательный порядок)

1. Задача уточняется главным агентом.
1a. `explore` (встроенный subagent) — локальный поиск по коду и зависимостям; только чтение.
1b. `researcher` (subagent) — только внешние источники; локальные файлы не читает. Привлекать,
    только когда внешние факты действительно добавят к проверяемому вопросу.
1c. `debugger` (subagent) — поиск первопричины по симптому и результатам проверок; код не меняет.
2. `planner` (subagent) — план, риски, необходимые проверки. Код не меняет.
3. `architect` (subagent) — архитектурная проверка плана до реализации. Код не меняет.
4. Главный агент реализует одобренный план — единственная роль, которая меняет файлы.
5. `/check` — стандартная или точечная проверка; результат передаётся `tester`.
5a. `tester` (subagent) — независимая оценка доказательств: не запускает команды, не меняет код
    и тесты, не превращает пропуск в прохождение.
6. `reviewer` (subagent) — проверка готового кода.
7. При замечаниях — исправления главным агентом и повторные `/check` и `/review`.

Агентов запускать только последовательно, по одному. Архитектурные решения и итоговые изменения
остаются за главным агентом и создателем проекта.

### Обязательное ожидание дочерней сессии

1. Coordinator запускает дочернего агента через `subagent`.
2. После получения `sessionID` Coordinator обязан дождаться завершения **одним блокирующим вызовом**
   `POST /api/experimental/session/{sessionID}/wait` через `opencode api post`. Это проверенный
   лабораторный способ; не предполагать, что endpoint автоматически доступен в любой конфигурации.
3. После завершения `wait` Coordinator получает результат дочерней сессии и продолжает работу.
4. Пока дочерняя сессия работает, повторно вызывать `subagent` с тем же `sessionID` запрещено.
5. Циклы опроса, повторные follow-up и периодические проверки состояния запрещены.
6. Если `wait` завершился ошибкой, переход к повторным вызовам запрещён: зафиксировать ошибку,
   сообщить о проблеме и остановить шаг до решения.

## Реестр находок

- Каждый дочерний отчёт сводится в нумерованный список: источник (`файл:строка` или URL), суть,
  статус (подтверждено / потенциально / ложное срабатывание / вопрос), доказательность
  (по коду / рантайм / непроверено), ограничения.
- Полный первичный реестр сохраняется в отдельном файле. Перед передачей указывать путь к нему.
  Следующий агент получает **полный первичный текст**, а не краткую сводку. Запрещено заменять
  первичные записи пересказами.
- При необходимости создавать отдельный консолидированный реестр, сохраняя соответствие
  исходным ID. Исходные ID и консолидированные записи учитывать раздельно.
- В итоговом отчёте раздельно указывать: количество исходных ID; количество консолидированных
  записей; количество отклонённых формулировок и причины отклонения; количество ID, не вошедших
  в итоговый реестр, если такие есть. Не смешивать единицы измерения.
- Перед завершением выполнять сверку: «исходные ID → зарегистрированные ID → отклонённые ID».
  Silent drop запрещён.
- Reviewer выполняет две раздельные проверки:
  - **Проверка передачи:** все ли исходные ID сохранены, сохранены ли источники, содержание,
    статусы и ограничения, нет ли искажений при консолидации.
  - **Проверка достоверности:** подтверждаются ли утверждения исходниками, достаточно ли
    доказательств, не выданы ли гипотезы за факты.
  Успешная проверка передачи не означает подтверждения достоверности всех находок.
- Рекомендация агента не является разрешением на изменение кода, тестов или конфигурации.
  Изменения выполняет только главный агент после согласованного плана.

## Проверки

- Сервер, из `/root/text-world`: `python3 -m compileall -q server`, `python3 -m pytest -q`, при необходимости `python3 -m server.doctor`.
- Клиент, из `/root/text-world/android`: `./gradlew --offline :app:testDebugUnitTest`.
- Завершать задачу только после `/check`, а если менялся код — дополнительно `/review`.
- Тесты и `pytest.ini` менять только по отдельной просьбе.

## Git

- `/root/text-world/android` — отдельный Git-репозиторий (`argo`).
- `/root/text-world` (сервер) сейчас **не** Git-репозиторий: не предполагать там `git diff` и не инициализировать репозиторий без разрешения.
- Не делать `push`, `reset --hard`, `clean -f`, force-push без явного разрешения.

## Формат ответов

Русский язык, коротко: что сделано, что проверено, что осталось.
